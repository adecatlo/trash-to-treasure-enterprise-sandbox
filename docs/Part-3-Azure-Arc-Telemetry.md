# Part 3: Azure Arc & Telemetry Ingestion

## Overview

After successfully configuring my Windows Server 2025 Domain Controller and Windows 11 Enterprise VM, my next goal was to connect the Windows infrastructure to Microsoft Azure and begin collecting security telemetry.

I onboarded both systems to Azure using Azure Arc and then began building the telemetry pipeline that would allow me to work with Microsoft security data and practice Kusto Query Language (KQL).

This phase became an important transition from building the infrastructure to actually using it for security monitoring and analysis.

---

## ☁️ Azure Arc Onboarding

Azure Arc was installed on both the Windows Server 2025 Domain Controller and Windows 11 Enterprise VM.

The onboarding process was relatively straightforward. One feature I found particularly useful was the option to install Azure Arc during the Windows Server setup process, which made onboarding the Domain Controller especially simple.

Once configured, both Windows systems appeared as connected resources within my Azure environment.

---

## 📊 Log Analytics Workspace

After onboarding the systems, I wanted to begin practicing KQL against actual security telemetry.

To do this, I created an **Azure Log Analytics Workspace (LAW)** and configured the initial data collection for my lab environment.

The Azure Monitor Agent (AMA) was subsequently installed on both Windows systems to collect telemetry and send it to the workspace.

This established the basic telemetry pipeline:

**Windows VMs → Azure Monitor Agent → Log Analytics Workspace**

---

## 🔎 An Unexpected Telemetry Difference

At this point, I encountered an unexpected issue while following the Microsoft Learn material I was using to study KQL.

The tables and queries available in my environment did not initially match the examples in the coursework.

For example, when looking through the available security-related data, I encountered an `Event` table rather than the `SecurityEvent` table used in many of the examples I was following.

Several of the KQL queries from my studies also did not correspond to the tables and fields available in my environment.

Initially, I wasn't sure why my lab differed from the Microsoft Learn examples.

After investigating the configuration, I realized that **Microsoft Sentinel was the missing piece**.

---

## 🛡️ Deploying Microsoft Sentinel

I deployed the Microsoft Sentinel free trial and connected it to the Log Analytics Workspace I had already created.

Once Sentinel and the associated security data collection were configured, the telemetry available in my environment aligned much more closely with the Microsoft Learn material I was studying.

This gave me access to the `SecurityEvent` table used in many of the KQL exercises and allowed me to begin applying KQL to security telemetry generated by my own lab.

This was an important lesson: simply creating a Log Analytics Workspace and collecting Windows events does not necessarily mean the data will appear in the same tables or schema used by a particular security training exercise. The data collection configuration and security services connected to the workspace also play an important role.

---

## 🔍 Beginning KQL Threat Hunting

With the telemetry pipeline established, I began practicing KQL using Microsoft Learn, SC-200 coursework, and additional resources.

One of the first exercises I worked with was looking for repeated failed authentication attempts against a specific account:

```kql
SecurityEvent
| where TimeGenerated > ago(24h)
| where Account == "Administrator"
| where EventID == 4625
| summarize Count=count() by Computer
| where Count >= 10
| order by Count desc
```

This query searches for failed logon events (Event ID 4625) associated with the `Administrator` account and summarizes the number of attempts by computer.

I also experimented with a query designed to identify patterns of repeated failed logons over time:

```kql
SecurityEvent
| where TimeGenerated > ago(7d)
| where EventID == 4625
| summarize Count=count()
    by Computer, Account, Hour=bin(TimeGenerated, 1h)
| where Count >= 5
| order by Count desc
```

This helped me understand how I could use KQL to identify patterns in failed logons that may warrant further investigation. For instance, a pattern like this could point to a potential brute-force attempt.

---

## 🧪 Generating Test Telemetry

Because my lab was not experiencing an actual brute-force attack, I wanted to see whether I could generate relevant security telemetry myself.

I intentionally entered incorrect passwords in my lab environment and was able to generate failed authentication events.

I then used the KQL query above to search for those events and was able to retrieve results from my own lab environment.

This was a useful transition from writing theoretical queries to seeing how KQL could be applied to actual security events generated by a controlled environment.

---

## 📚 Lessons Learned

This phase of the project reinforced several concepts for me:

* Azure Arc provides a straightforward method for onboarding on-premises virtual machines into Azure.
* Azure Monitor Agent provides a mechanism for collecting telemetry from the Windows systems.
* Log Analytics Workspace provides the platform for storing and querying collected telemetry.
* Microsoft Sentinel provides the security operations layer I needed for the exercises I was following.
* The tables and schemas available for analysis depend on how telemetry collection and security services are configured.
* KQL can be used to filter, summarize, and identify patterns within security telemetry.
* Generating controlled test events is a useful way to validate KQL queries in a lab environment.
